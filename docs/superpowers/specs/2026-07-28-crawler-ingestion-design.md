# 외부 공고 크롤링 수집 설계

작성 2026-07-28 · 브랜치 `worktree-crawler-ingestion`

## 목적

여우알바(m.foxalba.com)의 공개 구인공고를 주기적으로 수집해 (1) 업소 영업 리드를 확보하고
(2) 서비스 초기의 공고 밀도를 채운다.

## 정찰 결과

구현 전에 실제 응답을 받아 확인한 사실이다. 추측으로 파서를 쓰면 전부 다시 쓰게 된다.

**여우알바** — `robots.txt`가 `User-agent: * / Allow: /`로 전면 허용. 목록은
`m.foxalba.com/all.asp`, 페이지네이션은 `?intpage=N`(페이지당 50건, 실측 총 3,283건),
상세는 `view.asp?o_idx={id}`. **인코딩이 EUC-KR**이라 `fetch().text()`로 읽으면 한글이 전부
깨진다. 상세에 담당자명·연락처·카톡아이디·사업자명·주소가 공개돼 있다.

**퀸알바** — `queenalba.net`. `robots.txt`에서 공고 상세가 `/guin_detail.php?num=`,
게시판이 `/bbs_detail.php?bbs_num=` 임을 확인했고, 개별 글 번호 열 몇 개가 콕 집어 Disallow
돼 있다(색인 삭제 요청 처리 흔적). 그러나 **사이트 전체가 KCB 본인확인 성인인증 게이트 뒤에
있다** — `index.php`가 JS로 `/adult_index.php`로 넘기고, 그 페이지는
`/okname/phone_popup2.php`(휴대폰), `/okname/ipin2.php`(아이핀), `kcbOutForm` 폼을 띄운다.
인증 전에는 공고·게시판 링크가 하나도 노출되지 않는다. 이를 자동으로 통과하려면 실제 사람의
본인확인을 봇에 심어야 하므로 **합법적 수집 경로가 없다.** 대상에서 제외한다.

> `robots.txt`의 `Allow: /`는 접근·색인에 대한 약속이지 재게시 허락이 아니다. 두 가지를 같은
> 근거로 쓰면 나중에 방어가 되지 않는다.

## 설계 판단

### 출처 구분은 컬럼이 아니라 테이블 경계

요청은 `0: 크롤링 / 1: 순수 / 2: 전환` 세 값이었지만, 이건 값 셋이 아니라 라이프사이클이다.
0은 우리 소유가 아니고 2는 우리 소유다.

`job_post`는 `organization_id`·`created_by_user_id`가 NOT NULL이라 크롤링 행에 붙일 주인이
없다. 합성 계정을 만들어 붙이면 그 조직이 업소 목록·검색·채팅·리뷰·통계 전반에 유령으로
섞이고, 그걸 걸러내는 조건을 한 군데라도 빠뜨리면 크롤링 공고에 결제창이 뜨거나 채팅방이 열린다.

그래서 크롤링 원본은 `crawled_job_post`에 따로 쌓고, `job_post`에는 `source`
enum(`original`/`converted`)과 `crawled_from_id`만 둔다. 업체가 실제로 가입해 전환될 때만
`job_post` 행이 생긴다. 값은 정수 대신 pgEnum 문자열로 뒀다 — 이 스키마는 전부 pgEnum이고,
나중에 쿼리에서 `source = 2`를 보면 그게 뭔지 아무도 기억하지 못한다.

### 만들지 않은 것 두 가지

**연락처의 공개 노출.** 수집은 하되 운영자 전용이다. 원본에 연락처를 올린 담당자는 그 사이트
이용자에게 연락받는 데 동의했을 뿐 다른 서비스에서의 재공개에 동의한 적이 없다. 업종 특성상
본인이 통제하지 못하는 확산은 실제 피해로 이어지고, 개인정보보호법 제17조(제3자 제공)에도
정면으로 걸린다. 영업 리드라는 목적은 운영자 열람만으로 온전히 달성된다. 실효를 위해
**본문에 박힌 전화번호·메신저 아이디도 마스킹**한다 — 유흥 공고는 본문에 연락처를 크게
박아두기 때문에 필드만 가리면 아무것도 가린 게 아니다.

**커뮤니티 글 전문의 게시판 삽입.** `community_post`는 `author_user_id`가 NOT NULL이고 글
비밀번호로 수정·삭제하는 클래식 게시판이다. 남의 글을 넣으려면 우리 회원 ID와 가짜 비밀번호를
붙여야 하고, 그러면 남이 쓴 글이 우리 회원의 얼굴로 게시판에 선다. 실제 회원이 거기 댓글을 달고
추천을 누르는데 원작자는 대화에 존재하지 않는다. 대신 `crawled_community_topic`에 제목과 반응
지표만 담아(본문 미저장) "어떤 주제가 실제로 반응을 얻는가"를 운영 참고자료로 쓰고, 시드 글은
운영이 직접 쓴다.

### 이미지는 1차 범위에서 제외

본문의 이미지 22개가 `fox2.kr`·`badalba.com` 외부 핫링크였고 일부는 http 평문이다. 핫링크는
남의 대역폭을 쓰면서 언제든 끊기고 mixed content가 되며, 우리 GCS로 복사하면 비용이 붙고
복제라는 사실이 가장 선명해진다. 본문은 HTML을 버리고 텍스트만 남긴다(원문이 `font` 태그·인라인
48px로 채워져 있어 그대로 렌더하면 우리 화면이 깨진다).

## 구조

| 파일 | 역할 |
|---|---|
| `bambi-crawl-fetch.ts` | HTTP 계층. EUC-KR 디코딩, robots 파싱·판정, 요청 간격, 재시도 |
| `bambi-crawl-foxalba.ts` | 사이트 파서. HTML 문자열만 받는 **순수 함수** |
| `bambi-crawl-normalize.ts` | 급여 파싱, 업종 매핑, 연락처 마스킹, 변경 해시 |
| `bambi-crawl-policy.ts` | 수집 여부·수율 신뢰·페이지 수 판정. DB도 네트워크도 안 건드린다 |
| `bambi-crawl-ingest.ts` | 회차 실행. 목록 패스 → 상세 패스 → 만료 |
| `apps/server/src/plugins/crawl.ts` | `@fastify/schedule` 틱 |
| `routers/bambi/crawler.ts` | 운영자 API |

파서를 순수 함수로 떼고 실제 응답을 픽스처로 저장한 게 설계의 핵심이다. DOM 크롤링의 운영
비용은 대부분 셀렉터가 소리 없이 깨지는 데서 나오고, 이 경계가 유일하게 작동하는 방어선이다.
픽스처의 담당자 실명·휴대폰·카톡아이디는 치환해 저장했다(리포에 개인정보를 영구 보관하지 않는다).

## 사고 방지

**전량 만료 방지.** 목록 파싱이 0건이면 "공고가 사라졌다"가 아니라 "셀렉터가 깨졌다"로 보고,
만료 처리와 생존 표시 갱신을 모두 건너뛴 채 `aborted_low_yield`로 중단한다. 상세 파싱 실패율이
절반을 넘을 때도 같다(표본 5건 미만이면 판단 보류). 원본에서 사라진 공고도 즉시 지우지 않고
`last_seen_at`이 3일 지나야 만료시킨다.

**멱등성.** `(source_site, source_external_id)` 유니크 + `content_hash`. 해시 재료는 원문
필드만 넣어 파싱 규칙을 고쳐도 전체 행이 "변경됨"으로 뒤집히지 않게 하고, 필드 경계는 NUL로
이어 `["ab","c"]`와 `["a","bc"]`가 같은 해시가 되는 것을 막는다.

**`last_seen_at`과 `detail_fetched_at` 분리.** 전자는 매 회차 목록으로 갱신되고 후자는 상세를
받았을 때만 갱신된다. 섞으면 재수집 판정이 무너진다.

**요청 예의.** 요청 간격 1.5초, 동시 요청 1, 연락처를 밝힌 User-Agent. `robots.txt`를 못
받으면 "규칙 없음"이 아니라 "전부 금지"로 본다. 개별 URL이 robots에서 막혀 있으면 실패가 아니라
존중할 의사표시로 보고 수율 판정에서 제외한다.

**On/Off는 DB에.** `bambi_site_settings.crawl_enabled`(기본 false). `toad-scheduler`의
`job.stop()`은 그 프로세스에서만 참이라 인스턴스가 둘이면 한쪽만 멈춘 채 다른 쪽이 계속 긁는다.
DB 플래그는 어디서 꺼도 모든 인스턴스에 즉시 반영된다.

**상한을 드러낸다.** 한 회차 상세 요청은 300건까지고(1.5초 간격 기준 약 7분), 남은 잔량은
로그로 남긴다. 조용히 자르면 "다 수집했다"로 읽힌다. 본문은 20,000자까지 저장한다(실측 샘플의
모집글이 한 줄에 77,000자였다).

## 급여 단위 TC

여우알바의 기본 급여 단위는 `TC`(테이블 차지)인데 우리 `payUnitOptions` 5종에는 없다. "일급"에
욱여넣으면 금액의 의미가 테이블당에서 하루당으로 바뀌므로 `crawled_job_post.payUnit`에 원문
그대로 둔다. 우리 5종으로 좁히는 판단은 전환 시점에 운영자가 한다. 여우알바의 업종 분류는 우리
`jobIndustryCategory` 8종과 같은 어휘라 매핑이 거의 1:1이다.

## 운영자 화면

`/moderator/crawler`에 수집 사용 토글, 수집 주기(시간), 즉시 수집, 상태별 현황, 최근 20회차를
둔다. 「수율 미달 중단」이 회차 목록에 뜨는 것이 셀렉터 파손을 알아채는 창구다.

**즉시 수집**은 주기 판정만 건너뛰고 마스터 스위치·중복 방지·수율 판정·만료 규칙은 예약 실행과
같은 경로를 지난다. 꺼둔 수집이 버튼 하나로 되살아나면 "껐다"는 말이 거짓이 되므로, 스위치가
꺼져 있으면 실행하지 않는다. 한 회차가 최대 10분쯤 걸려 응답을 붙잡지 않고 시작만 시킨 뒤
돌려주며, 화면은 회차 목록을 다시 불러 진행 상황을 본다.

동시 실행은 `crawl_run`의 **부분 유니크 인덱스**(`status = 'running'`)가 막는다. 애플리케이션
검사만으로는 두 요청이 동시에 통과하는 창이 남지만, DB가 직렬화 지점을 잡으면 두 번째 INSERT가
실패하고 수집기가 그것을 "이미 실행 중"으로 처리한다. 서버가 회차 도중 죽어 `running` 행이
남으면 30분 뒤 실패로 정리돼 스스로 풀린다.

## 남은 작업

1. **마이그레이션 생성·적용** — `db:generate` → `db:migrate`(사용자가 실행). 다음 번호는 0042.
2. **전환 액션** — `crawled_job_post` → `job_post` 생성(`source='converted'`).
3. **수집 목록 화면** — 라우터(`list`/`getLead`/`setIndustryCategory`)는 준비됐고 화면이 없다.
4. **공개 노출** — 목록에 출처 배지·원문 링크와 함께 노출. 유료 광고 정렬 아래.
5. **게시판 주제 수집** — 여우알바 `/board/index.asp` 파서. 테이블은 준비돼 있다.
6. **이용약관 확인** — `robots.txt`는 확인했으나 약관은 아직이다.
7. **User-Agent 연락처** — 배포 전 `bambi-crawl-fetch.ts`의 예시 주소를 운영 이메일로 바꾼다.
