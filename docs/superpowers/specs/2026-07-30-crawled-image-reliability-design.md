# 수집 상세 이미지 신뢰성 · 카드 단위 뱃지 설계

2026-07-30. 사용자 보고: "크롤링할 때 공고 상세 이미지를 못 가져오는 경우가 있다"(다장
업로드 공고 포함), "맞는 셀렉터를 줬는데도 못 가져오는 공고가 있다", "카드 unit 뱃지가
안 붙는 공고가 있다".

## 실측 진단 (dev DB 300건 + 실물 상세 HTML 재현)

수집 300건 중 **107건이 상세 이미지 0장**. 실패 공고의 실물 HTML을 받아 현재 파서
로직으로 재현한 결과, 파서(앵커·중첩 구조)는 정상이고 원인은 세 갈래다:

| # | 유형 | 근거 | 영향 |
|---|------|------|------|
| 1 | **대형 전단이 한 장 상한 2MB 초과** | 32747→4.62MB, 9154→3.30MB, 36655→2.10MB (전부 HTTP 200 정상 JPG) | 0장 공고의 주범. `embedCrawledImage`가 조용히 null → 이미지 없는 공고와 구분 불가 |
| 2 | **본문 이미지가 외부 CDN 호스팅** | 37893: 본문 14장 전부 `tksk8080.diskn.com` | same-origin 화이트리스트가 전부 거름. 열어도 robots.txt 없는 호스트는 "전부 금지" 폴백에 걸림 |
| 3 | **커버리지 상한·우선순위 부재** | 목록 681건 vs `MAX_DETAIL_FETCHES_PER_RUN` 300, 대상 정렬 없음 | 신규 공고(예: 사용자가 든 "디저트 강훈팀")가 재수집 뒤로 밀려 아예 미수집 |

사용자가 든 강훈팀 공고의 중첩 구조(링크 안 이미지·내부 div)는 현 파서의 `find("img")`가
이미 전부 훑는다 — 그 공고의 문제는 #3(미수집)이다. nth-child 셀렉터는 쓰지 않는다(기존
앵커 방식 유지 — 제목 이미지 `title_detail_guin_02` 기준이 광고 칸 증감에 안전).

카드 뱃지: `visual-job-card.tsx`의 `PAY_UNITS`가 시급·일급·주급·월급·급여·연봉뿐이라
**건당(47건)·TC** 카드가 뱃지 없이 렌더된다.

## 설계 결정

### D1. 이미지 용량 상한 상향 (원인 #1)
- `CRAWLED_IMAGE_MAX_BYTES` 2MB → **8MB**, `CRAWLED_IMAGE_TOTAL_MAX_BYTES` 8MB → **16MB**.
- 근거: 실측 최대 4.62MB에 여유 2배. base64 +33%를 감안해도 상세 응답 상한 ~21MB —
  상세 화면 전용 컬럼 규율(목록 쿼리 금지)이 이미 있어 목록 성능과 무관.
- 초과분은 지금처럼 failed로 집계·경고 로그. 리사이즈(이미지 라이브러리)는 의존성 추가
  금지 원칙으로 비채택, 장기적으로 GCS 이전 시 재검토.

### D2. 외부 호스트 본문 이미지 폴백 (원인 #2)
- 파서(`readDetailImageUrls`): 화이트리스트 same-origin 이미지가 **한 장이라도 있으면
  그것만**, **한 장도 없으면 외부 호스트(http/https, 타 오리진) 이미지로 폴백**.
  - 혼합 공고(본문 이미지 + imgur 장식 gif)는 기존대로 same-origin만 남아 장식이 안 샌다.
  - 전량 외부 호스팅 공고(37893류)만 외부 폴백이 열린다. same-origin 비화이트리스트
    (에디터 아이콘 `/cheditor/`·`/Editor/`, 사이트 장식 `/img/`)는 폴백에서도 제외.
- 미디어 계층의 SSRF 차단·매직바이트 판정·용량 상한은 외부 호스트에 그대로 적용된다.
- `loadRobots`: robots.txt **4xx 응답 → 규칙 없음(허용)** 으로 변경(RFC 9309 §2.3.1.3 —
  4xx는 "규칙이 없다"는 뜻이다). 네트워크 오류·5xx·타임아웃은 기존대로 전부 금지 유지.
  외부 CDN은 robots.txt가 404인 경우가 대부분이라 이 변경 없이는 D2가 무의미하다.

### D3. 상세 수집 우선순위 (원인 #3)
- `pickDetailTargets` 결과를 정렬: **미수집(detailFetchedAt null) 먼저, 그다음 오래된
  순**. 회차당 300 상한은 유지(상대 서버 부하 정책) — 정렬만으로 신규 공고가 재수집에
  밀려 굶는 문제가 사라진다.
- 기존 0장 107건의 백필: 병합 후 dev DB에서 해당 행의 `detail_fetched_at`을 null로
  리셋(일회성 운영 조치, 코드 아님) → 다음 즉시수집 두 회차 안에 신규 상한과 함께 소화.

### D4. 카드 단위 뱃지 일반화
- `splitPay`: 알려진 목록에 없어도 **머리 토큰이 숫자 없는 1~4자이고 꼬리가 숫자로
  시작하면 단위로 인정** — 건당·TC·협의(금액 병기)·향후 새 단위까지 뱃지로 렌더.
  기존 목록 매칭("급여 협의"의 "급여" 등)은 그대로 우선.
