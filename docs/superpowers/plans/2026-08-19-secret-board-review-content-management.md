# 비밀글 게시판·후기 포인트·콘텐츠 이력·공고 상세 개선 Implementation Plan

## 목표

비밀글 게시판을 본인인증 성인 전용 익명 공간으로 추가하고, 일반 사용자에게는 성별 아이콘과
`밤비`만 노출하면서 Admin에게만 검증된 실명 정보를 제공한다. 기존 신고 UI를 대상 중심 3단
구조로 정리하고, 후기의 공고당 1회 작성·작성 포인트·후기별 유료 열람을 포인트 원장과 원자적으로
연결한다. 회원과 Admin의 콘텐츠 이력을 보존하며, 일반·수집 공고 상세를 `공고 설명 → 후기 →
안전 확인` 순서와 접힌 설명 미리보기로 통일한다.

이 문서는 이후 구현의 정본이다. 구현 중 임의로 정책을 바꾸지 않으며, 변경이 필요하면 구현 전에
사용자에게 확인하고 이 문서를 먼저 갱신한다.

## 공통 원칙

- 기존 동적 게시판, 비회원 인증, 커뮤니티 작성, 신고, 후기, 알림, 포인트 원장,
  `PageControls`, `AlertDialog`, 소프트 삭제 로직을 재사용한다.
- 게시판명·경로·역할 라벨·포인트·색상·페이지 크기·설명 접힘 기준을 화면마다 하드코딩하지 않는다.
  DB 설정, 공용 정책, 공용 라벨 맵, 디자인 토큰과 이름 있는 상수를 정본으로 사용한다.
- 비밀글 특수 판정은 `secret` 문자열 비교를 여러 화면에 흩뜨리지 않고 공용 정책 함수에서 제공한다.
- 서버가 권한·실명·성별·포인트·유일성의 최종 정본이다. 클라이언트 입력을 신뢰하지 않는다.
- 개인정보는 최소 응답 원칙을 적용하고 Admin 전용 프로시저 외에는 실명·전화번호를 반환하지 않는다.
- DB 변경은 `db:push`가 아니라 Drizzle migration으로만 처리한다.

## 확정 요구사항

### 비밀글 게시판과 배치

- 저장 key와 slug는 `secret`, 주소는 `/seeker/community/secret`, 라벨은 `비밀글`이다.
- 공지사항은 최상단 전폭 한 칸이다.
- 데스크톱은 그 아래 `베스트글 · 자유수다 · 밤문화 이야기`, 다음 줄은
  `비밀글 · 중고거래 · 무료 법률 자문`을 각각 3열로 배치한다.
- 모바일은 기존 반응형 관례대로 한 열로 쌓고 위 순서를 유지한다.
- 운영자가 추가한 동적 게시판은 기본 1-3-3 영역의 순서를 깨지 않고 그 아래부터 기존 방식으로
  이어 붙인다. 동적 게시판끼리의 순서는 DB `sort_order`를 따른다.
- 비밀글은 삭제할 수 없는 빌트인 게시판으로 만들되 운영자 게시판 관리에서 아이콘·설명·활성·
  작성 가능 여부·순서를 기존 게시판과 같은 방식으로 관리한다.
- 비밀글 아이콘은 Lucide 공식 `MessageSquareLock`을 사용한다. 기존 아이콘 레지스트리와
  `text-coral-500` 색상·크기를 그대로 재사용하며 별도 PNG/SVG 예외를 두지 않는다.
- 운영자가 만든 동적 게시판은 계속 DB 목록을 정본으로 사용한다. 새 게시판은 별도 배선 없이
  콘텐츠 게시판 관리와 기타 포인트 설정의 게시판별 작성 포인트에 자동 노출돼야 한다.

### 접근과 본인인증

- 비밀글은 성인 본인인증과 `male` 또는 `female` 성별이 확인된 사람에게 역할·성별과 관계없이
  열람·글·댓글 작성을 허용한다.
- 대상은 남녀 인증 비회원, 구직자, 구인자, 법률자문가, Admin이다.
- 현재 남성 구직자·법률자문가·비회원에게 적용되는 일반 게시판 제한보다 비밀글 전용 정책을 우선한다.
- 비회원은 글과 댓글만 작성할 수 있고 신고는 로그인 회원만 할 수 있다.
- 성별 또는 성인 인증이 확인되지 않으면 비밀글 열람·작성에 진입할 수 없고 본인인증으로 안내한다.
- 기존 회원에게 검증 실명이 없으면 비밀글 최초 이용 시 한 번만 재인증한다. 저장 후 재인증하지 않는다.
- 앞으로 인증하는 비회원과 신규 회원은 최초 본인인증 때 실명·전화번호·성별을 함께 저장한다.

### 익명 표시와 Admin 신원 확인

- 비밀글의 글·댓글 작성자 표시명은 입력값이나 계정 닉네임과 무관하게 항상 `밤비`다.
- 개인 프로필 사진은 사용하지 않는다.
- 남성은 검은 남성 기호와 파란 계열 연한 배경, 여성은 검은 여성 기호와 primary 연한 배경을 쓴다.
- 색상은 디자인 토큰으로 관리하고 픽셀·색상 리터럴을 컴포넌트에 직접 넣지 않는다.
- 글 목록, 상세, 댓글, 대댓글, 신고 대상 카드 등 모든 비밀글 작성자 표현이 같은 공용 컴포넌트를 쓴다.
- 일반 사용자와 비회원에게 실제 user id, guest id, 실명, 전화번호를 응답하거나 DOM에 숨겨 두지 않는다.
- Admin만 `밤비` 작성자 표시를 클릭/터치해 검증 실명을 확인할 수 있다.
- 일반 비밀글 상세의 Admin 신원 팝오버에는 실명만 표시한다.
- 비밀글 신고 검토에서는 피신고자와 신고자의 `실명 · 전화번호`를 표시한다.

### 신고 목록과 상세

- 비밀글의 글과 댓글은 기존 커뮤니티 신고 생성·상태·조치 로직을 재사용한다.
- 신고자는 로그인 회원만 가능하며, 비회원 신고 테이블 확장은 하지 않는다.
- 신고 목록의 대상 라벨과 게시판 라벨은 DB 게시판 정본과 공용 라벨 함수를 사용한다.
- 신고 상세 오른쪽 대상 영역은 채팅·커뮤니티 모두 다음 3단 구조로 통일한다.
  1. 대상 콘텐츠 카드
  2. 피신고자 카드
  3. 신고자 카드
- 채팅 신고:
  - 1단은 채팅 아이콘, 채팅방을 식별하는 제목, `채팅방` 라벨이다.
  - 2단은 피신고자의 실제 닉네임과 역할, `피신고자 · 구직자/구인자`를 표시한다.
  - 3단은 신고자의 실제 닉네임과 역할, `신고자 · 구직자/구인자`를 표시한다.
  - 기존처럼 피신고자 이름 대신 채팅방 제목을 반복하거나 `피신고자 · 채팅방`으로 표시하지 않는다.
- 일반 커뮤니티 신고:
  - 1단은 문서 아이콘, `커뮤니티 글 · 제목`, `커뮤니티 글`이다. 댓글 신고도 원문 글 제목을 기준으로 한다.
  - 2단은 작성자 프로필 표현·닉네임·역할과 `피신고자 · 작성자`다.
  - 3단은 신고자 프로필 표현·닉네임·역할과 `신고자 · 역할`이다.
- 비밀글 신고:
  - 1단은 문서 아이콘, `커뮤니티 글 · 제목`, `비밀글`이다.
  - 2단은 성별 아이콘, `실명 · 전화번호`, `피신고자`다.
  - 3단은 성별 아이콘, `실명 · 전화번호`, `신고자`다.
  - 글 신고는 제목과 본문, 댓글 신고는 원문 글 제목과 신고된 댓글을 기존 상세 본문 영역에서 보여준다.
- 탈퇴·삭제 뒤에도 신고 당시 대상과 신원을 검토할 수 있도록 필요한 표시값은 신고 snapshot에 보존한다.
  live join 결과가 있으면 최신 상태를 쓰고, 없으면 snapshot을 사용한다.

### 검증 신원 데이터

- 본인인증 결과의 검증 실명, 전화번호, 성별을 서버가 저장한다.
- 기존 `user.name`은 닉네임일 수 있으므로 실명 정본으로 사용하지 않는다.
- 기존 identity log는 이름을 저장하지 않는 감사 로그이므로, 비밀글 신원 조회용 별도 정본을 둔다.
- 회원은 user id, 비회원은 서명된 guest token의 gid에 연결한다. 정확히 한 주체만 연결되도록 DB CHECK를 둔다.
- 전화번호·성별·실명은 포트원 서버 조회 결과만 저장하며 클라이언트 제출값으로 덮지 않는다.
- 비회원 토큰에는 실명·전화번호를 싣지 않는다. 토큰은 gid·성별·만료만 유지한다.
- 일반 API는 `hasVerifiedSecretIdentity` 같은 최소 boolean과 성별 표시 정보만 반환한다.
- Admin 신원 조회는 adminProcedure와 감사 가능한 대상 id를 요구한다.

### 후기 작성 유일성과 등록 확인

- 구직자는 하나의 공고에 후기 하나만 작성할 수 있다.
- 현재 채팅방+작성자 유니크를 공고+작성자 유니크로 강화한다. 채팅방을 나가 새 방을 만들어도 추가 후기를 막는다.
- 후기 자격은 구인자가 면접을 `completed`로 완료한 경우에만 인정한다. 단순 confirmed는 부족하다.
- 등록 버튼을 누르면 저장 전에 AlertDialog를 띄운다.
- 다이얼로그는 한 번 등록한 후기는 사용자가 삭제하거나 다시 작성할 수 없음을 명확히 알린다.
- 확인을 누른 경우에만 기존 create mutation을 실행하고 취소하면 아무것도 저장·지급하지 않는다.
- 사용자 후기 삭제 기능은 추가하지 않는다.
- 운영자가 숨겨도 같은 공고에 새 후기를 작성할 수 없다.
- 후기 게시 정책은 유지한다. 정상 후기는 즉시 `published`, 위험 표현이 감지된 후기만
  `pending_review`로 저장되어 운영자 검수를 받는다.

### 후기 작성 포인트

- 기타 포인트 설정에 `후기 작성 포인트`를 추가하며 운영자가 정한 0 이상의 정수를 사용한다.
- 후기 insert와 포인트 지급은 같은 DB 트랜잭션으로 처리한다. 저장 실패·취소·페이지 이탈에는 지급하지 않는다.
- `published`와 `pending_review` 모두 저장 성공 시 지급한다.
- 운영자가 후기를 `hidden`으로 바꾸면 지급 포인트를 회수하고, 다시 `published`로 바꾸면 재지급한다.
- 사용자 삭제 기능은 없지만 포인트 서비스는 미래의 삭제 상태에도 같은 회수 불변식을 적용할 수 있게 설계한다.
- 원장 external key는 후기 id와 지급/회수 사이클을 식별하고, 같은 상태 전이의 재시도·일괄 처리에서
  중복 지급·중복 회수를 막는다.
- 지급·회수는 기존 사용자 advisory lock과 최대 보유 포인트 정책을 재사용한다.
- 지급액은 후기 작성 시점 설정값을 review의 `points_awarded` 스냅샷으로 보존한다.
- 숨김 시 현재 설정값이 아니라 실제 지급 스냅샷만 회수하고 0으로 만든다. 복구 시에는 최초 금액을
  복원하지 않고 재게시 시점의 최신 `후기 작성 포인트` 설정값을 최대 보유 포인트 범위에서
  다시 지급해 새 스냅샷으로 기록한다.
- 후기 지급 알림: `포인트 N이 지급되었어요! - 후기 작성` 의미를 공용 알림 라벨로 제공한다.
- 운영자 숨김 회수 알림은 숨김 사유와 `포인트 N이 차감되었어요 ㅠㅠ - 후기 숨김` 의미를 포함한다.
- 재게시 지급도 금액과 재게시 사유를 알린다.
- 알림 금액은 실제 원장 반영액을 사용한다. 상한 때문에 일부만 지급되면 실제 금액을 표시한다.

### 다른 구직자의 후기 유료 열람

- 기타 포인트 설정에 `다른 구직자 후기 열람 포인트`를 추가하고 기본값은 10P다.
- 값은 DB 설정 정본이며 코드에 10을 직접 넣지 않는다.
- 구직자는 본인이 작성한 후기는 별점과 본문을 무료로 본다.
- 다른 구직자의 각 후기 카드를 누를 때마다 설정된 포인트를 한 번 차감하고 해당 후기만 공개한다.
- 같은 공고에 후기 10개가 있고 모두 열면 각 10P, 총 100P를 사용한다.
- 현재 페이지 생명주기 동안 이미 결제한 review id 집합을 클라이언트 메모리에 유지해 재클릭은 재차감하지 않는다.
- 새로고침, 라우트 이탈, 재진입 시 공개 집합을 복원하지 않는다. DB에 영구 열람권을 저장하지 않는다.
- 결제 AlertDialog 문구는 다음을 그대로 사용한다.
  `후기를 확인하기 위해서는 Npt를 사용해야합니다! 이 페이지를 나갔다 오시면 다시 포인트를 사용하셔야 해요. 꼼꼼히 확인하세요!`
- AlertDialog에는 확인·취소 버튼이 있고, 확인 시 서버 차감 성공 후에만 해당 후기를 공개한다.
- 잔액 부족, 설정 비활성, 동시 차감 충돌 시 공개하지 않고 서버 오류를 사용자 문구로 안내한다.
- 별점과 본문을 모두 블라인드한다. 본문은 내용을 식별할 수 없을 정도로 강하게, 별점은 호기심을
  유도할 정도로 더 옅게 가린다. 단순 CSS blur 뒤에 원문을 내려보내지 않는다.
- 잠긴 후기 목록 API는 id·작성일·잠금 표시용 최소 메타만 내리고 별점·본문은 제외한다.
- 결제 API가 advisory lock 안에서 포인트를 차감한 뒤 해당 후기 본문과 별점을 한 번 응답한다.
- 이 열람은 소비 거래이므로 최대 보유 포인트가 아니라 잔액 부족 방지만 적용한다.
- 원장은 후기 id와 공고 id를 description에 남기되 영구 열람권으로 사용하지 않는다.
- 구인자는 자기 공고의 후기를 무료로 전부 열람하고 Admin도 무료로 전부 열람한다.

### 내 정보 글 관리

- 구직자와 구인자의 내 정보 메뉴·허브에 `글 관리` 버튼을 추가하고 같은 공용 화면을 사용한다.
- 화면은 `좋아요 누른 글`과 `내가 작성한 글`을 분리한다.
- 각 목록은 10개씩 서버 페이지네이션하며 기존 `PageControls`의 `< 숫자 입력 / 전체 페이지 >`를 재사용한다.
- 목록 항목은 게시판 라벨, 제목, 상태, 작성일 등 식별에 필요한 최소 정보를 표시한다.
- 정상 글을 누르면 현재 DB 게시판 slug와 post id의 실제 상세로 이동한다.
- 좋아요를 취소한 글은 좋아요 목록에서 빠진다.
- 좋아요를 누른 뒤 글이 삭제·숨김·이동되어도 이력 행은 목록에서 지우지 않는다.
- 본인이 작성한 글을 삭제해도 작성 이력에서 지우지 않는다.
- 이동·삭제·숨김 등으로 원래 링크를 열 수 없으면
  `게시판에서 글이 삭제되었거나 이동되어 불러올 수 없습니다`를 표시한다.
- 이력 보존을 위해 좋아요 FK cascade에 의존하지 않고 필요한 게시판·제목 snapshot을 보존한다.
- 비밀글 작성 글도 본인 목록에는 나타나지만 일반 사용자 화면에서는 작성자 실명을 노출하지 않는다.
- 글 관리 대상은 게시글이며 댓글 좋아요는 포함하지 않는다.

### Admin 회원 상세 콘텐츠 이력

- 회원 상세에서 제재 이력 아래에 `작성 콘텐츠 이력`을 추가한다.
- 제재 이력과 작성 콘텐츠 이력은 모두 기본 접힘 Accordion이다.
- 제재 이력의 기존 10개 페이지네이션은 유지한다.
- 작성 콘텐츠 이력은 글과 댓글을 통합 최신순으로 조회하고 `전체 / 글 / 댓글` 필터를 제공한다.
- 10개씩 페이지네이션하고 기존 `PageControls`를 재사용한다.
- 게시 중, 숨김, 삭제됨 상태를 모두 표시한다.
- 사용자가 직접 삭제한 항목, 운영자가 숨김·삭제한 항목, 비밀글 글·댓글을 모두 포함한다.
- Admin에게만 비밀글 작성자의 실제 회원 연결을 보여준다. 일반 회원용 API와 컴포넌트는 재사용하지 않는다.

### 공고 상세 순서와 설명 접기

- 일반 등록 공고와 수집 공고 모두 본문 순서를 `공고 설명 → 후기 → 안전 확인`으로 통일한다.
- 수집 공고도 후기 섹션 제목과 빈 상태를 표시해 접힌 설명 아래에 `후기` 제목이 빼꼼 보이게 한다.
- 공고 설명은 데스크톱과 모바일에서 초기 접힘 상태다.
- 첨부 참고 이미지의 빨간선 위치를 시각 기준으로 삼되 픽셀을 컴포넌트에 산재시키지 않는다.
  공용 설명 접기 컴포넌트의 반응형 CSS 변수/이름 있는 토큰으로 접힘 높이를 관리한다.
- 접힌 상태에서는 내용 아래쪽에 gradient와 눈에 띄는 `더보기` 버튼을 표시한다.
- `더보기`를 누르면 전체 설명을 자연 높이로 펼치고 후기·안전 확인은 아래로 밀린다.
- 접힌 높이보다 짧은 설명에는 더보기 버튼이나 불필요한 빈 공간을 표시하지 않는다.
- 텍스트 설명, Tiptap block, 세로 상세 이미지 모두 같은 외곽 접힘 컨테이너를 사용한다.
- 원문 이미지 자체를 자르거나 변형하지 않고 컨테이너 overflow만 제어한다.
- 설명 펼침은 현재 페이지 UI 상태이며 영구 저장하지 않는다.

## 데이터 설계

### community_board seed

- migration에서 `secret` 빌트인 행을 다음 사용 가능한 sort order에 추가하고 기존 여섯 게시판의
  정렬값을 요구 순서로 명시적으로 재정렬한다.
- 애플리케이션 seed도 같은 정본 값을 사용하되 중복 상수는 공용 seed 자료구조로 모은다.
- 새 동적 게시판은 현재처럼 `community_board` 행 생성만으로 포인트 설정과 콘텐츠 관리에 나타난다.

### 검증 신원 정본

- 최신 develop PR #212가 추가한 `bambi_identity_verification_log.name`을 실명 정본으로
  재사용한다. 별도 검증 신원 테이블을 만들지 않는다.
- 회원은 `bambi_profile.birth_date/phone_number`와 인증 로그의 동일 필드를 서버에서 조인한다.
- 비회원은 인증 로그에 nullable unique `guest_id`만 추가해 서명 게스트 토큰의 gid와 연결한다.
  토큰에는 실명·전화번호를 싣지 않는다.
- 회원의 검증 신원은 탈퇴 즉시 일반 서비스 사용을 막고, 기존 사이트 설정의 `탈퇴 개인정보
  보존기간` 동안만 재가입·재로그인 차단과 신고/분쟁 처리 목적으로 분리 보관한 뒤 기존 탈퇴 계정
  파기 배치에서 함께 제거한다. 설정이 없으면 기존 기본값 30일을 사용하고 운영자 설정 범위
  1~365일을 그대로 따른다.
- 비회원 검증 신원은 기존 게스트 인증 유효기간과 같은 인증 후 30일까지 보관하고 만료 정리한다.
  게스트 쿠키가 로그인·로그아웃으로 먼저 사라져도 일반 서비스에서는 즉시 사용할 수 없으며,
  정리 시각까지의 잔여 데이터는 재노출하지 않는다.
- 신고가 접수된 경우에만 신고 당시 실명·전화번호·성별 snapshot을 신고 기록에 분리 보관한다.
  기존 개인정보 처리방침의 `소비자의 불만 또는 분쟁처리에 관한 기록 — 3년`을 적용하고 목적 외
  조회를 막는다. 3년 경과 파기 대상에 포함한다.
- 개인정보 처리방침의 수집 항목·목적·비회원 보유기간에 검증 실명과 secret 신고 처리 내용을
  추가하고, 실제 purge 동작과 문구가 일치하도록 함께 갱신한다.
- 실명과 전화번호는 Admin 전용 서비스 외 select 목록에 포함하지 않는다.

### 후기와 포인트 설정

- review에 `points_awarded integer not null default 0`을 추가한다.
- `(job_post_id, reviewer_user_id)` unique index를 추가한다. 기존 중복 데이터가 있으면 migration 전
  읽기 전용 점검으로 탐지하고 임의 삭제하지 않는다.
- site settings에 `review_write_points integer not null default 0`,
  `review_view_points integer not null default 10`을 추가하고 0 이상 CHECK에 포함한다.
- 후기 열람은 세션성이라 unlock 테이블을 만들지 않는다. 차감 원장만 감사 기록으로 남긴다.

### 콘텐츠 이력

- 커뮤니티 글·댓글은 현재 status 기반 소프트 삭제를 유지한다.
- 좋아요 대상 삭제 뒤에도 목록을 보존할 수 있도록 별도 like history snapshot을 정본으로 추가한다.
  현재 좋아요 FK의 cascade와 운영자 영구 삭제가 실행돼도 snapshot은 유지하며, post id, 당시 board
  key/slug, title, likedAt을 보존한다. 좋아요 취소 시 활성 목록에서는 제외하되 감사 목적의 불필요한
  개인정보는 남기지 않는다.
- snapshot은 post id, 당시 board key/slug, title을 보존하고 현재 글이 존재하면 live 값을 우선한다.

## API와 서비스 경계

- `bambi-secret-identity` 서비스: 기존 인증 로그의 회원/게스트 연결, 성별 표시 DTO, Admin 실명 조회.
- `bambi-community-access/authz`: secret board의 성인·성별·역할 예외를 공용 판정으로 제공.
- community create/update/comment 응답 조립: secret에서는 서버가 `밤비`, 성별 avatar DTO를 강제.
- community board router: built-in 삭제 금지, 동적 게시판 자동 포인트 노출 유지.
- moderation router: 신고 대상 3단 DTO와 secret Admin PII DTO, review 상태 전이와 포인트 원자화.
- reviews router:
  - create 전 completed 면접과 공고+작성자 유일성 확인.
  - insert+포인트 지급 트랜잭션.
  - 목록은 viewer role과 reviewer id에 따라 own/free/locked DTO 분리.
  - 후기별 unlock mutation은 차감 후 단건 민감 본문 반환.
- point settings router: 후기 작성·열람 값을 기존 전역 설정 저장에 포함.
- content history router: 내 좋아요/작성 글과 Admin 글·댓글 이력을 별도 권한 DTO로 제공.

## 핵심 테스트

- 남녀 인증 비회원과 모든 회원 역할이 secret을 열람·작성하고 미인증·성별 없음은 거부된다.
- 일반 게시판의 기존 남성/법률자문/게스트 제한은 변하지 않는다.
- secret 글·댓글은 어떤 닉네임·프로필 사진 입력에도 `밤비`와 검증 성별 아이콘만 보인다.
- 일반 API/HTML에 실명·전화번호가 없고 Admin API만 권한 확인 후 반환한다.
- 비회원은 작성 가능하지만 신고 요청은 거부되고 로그인 회원 신고는 성공한다.
- 동적 게시판 생성 즉시 콘텐츠 관리와 게시판별 포인트 설정에 나타난다.
- 채팅·일반 커뮤니티·비밀글 신고 상세가 각각 정확한 콘텐츠/피신고자/신고자 3단 구조다.
- 비밀글 신고는 양쪽 실명·전화번호를 보이고 일반 신고에는 불필요한 PII가 없다.
- 같은 구직자가 같은 공고의 다른 채팅방으로 후기 생성을 시도해도 DB/API가 막는다.
- completed 전에는 후기 저장과 포인트 지급이 모두 실패한다.
- 등록 AlertDialog 취소는 후기·포인트·알림을 만들지 않는다.

## 회원 등급 GIF 아이콘 추가 설계

- `bambi_member_grade`에 공개 GIF의 `icon_storage_key`를 nullable로 저장한다. URL 문자열을
  정본으로 저장하지 않고 기존 공개 버킷 URL 해석기를 재사용해 환경별 주소 하드코딩을 피한다.
- 운영자 전용 업로드 인텐트는 GIF만 허용하고 파일 크기·확장자·MIME을 서버에서 검증한다.
  등급 id 전용 storage prefix로 소유권을 확인한 뒤에만 update가 해당 키를 저장한다.
- 새 아이콘으로 교체하거나 등급을 삭제하면 더 이상 참조하지 않는 기존 객체를 공개 버킷에서
  정리한다. 로컬 저장소 미구성 환경에서는 프로젝트에 포함한 기본 GIF URL을 시드 값으로 쓴다.
- 운영자 등급 표에서 등급명 바로 앞에 아이콘을 표시하고 수정 Dialog에서 GIF 선택·미리보기·
  제거를 제공한다. 생성 폼도 선택적 GIF를 받을 수 있으나 업로드는 생성된 등급 id를 기준으로
  수행하므로 등급 생성 후 수정에서 등록하는 흐름을 기본으로 한다.
- 공용 `GradeBadge` 입력 타입에 `iconUrl`을 추가하고, API의 등급 조회·회원 등급 계산 결과가
  같은 필드를 전달한다. 아이콘이 없으면 기존 텍스트 뱃지만 그대로 표시한다.
- 기본 5개 등급은 새싹(잎 흔들림), 일반(브론즈 별 맥동), 우수회원(실버 메달 광택),
  열혈회원(불꽃 흔들림), VIP(왕관 보석 반짝임)의 투명 반복 GIF를 사용한다.
- GIF는 생성한 4프레임 스트립을 동일 프레임 크기로 정리하고 작은 아이콘 크기에서도 윤곽이
  뭉개지지 않도록 축소·팔레트 최적화한다. 원본 워터마크 이미지는 사용하지 않는다.

## 수다방 홈 행 배치 GUI 추가 설계

## 본인인증 실명 반출 금지 정책 변경

- `bambi_identity_verification_log.name`은 제한된 담당자만 DB에서 직접 확인하는 정보다. 웹 UI,
  운영자 화면, 일반 API 응답, 알림 metadata, 신고 snapshot으로 절대 반환하거나 복제하지 않는다.
- 신고 추적에는 본인인증 전화번호를 사용한다. 일반 게시판 회원은 닉네임, 비밀글 회원은 `회원`,
  비회원은 `비회원`으로만 표시하고 다음 줄에 전화번호를 표시한다. 성별 아이콘은 유지한다.
- 채팅 신고는 닉네임·전화번호·역할만 표시하며 실명 괄호 표기를 제거한다.
- 비밀글 상세의 Admin `밤비 → 실명` 토글과 실명 조회 procedure를 제거한다. Admin도 공개 화면에서는
  다른 사용자와 동일하게 `밤비`만 본다.
- 인증 완전성 판정은 이름이 저장되어 있는지만 서버 내부에서 확인할 수 있지만, 반환 객체에는 이름을
  select하거나 싣지 않는다.
- 기존 `report.target_snapshot`의 `reporterIdentity`, `authorIdentity`, `secretIdentity` 안에 저장된
  `realName`·`name` 키는 후속 migration으로 모두 삭제한다. 본인인증 로그 원본 행은 변경하지 않는다.
