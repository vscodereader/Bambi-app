## 4. 구현 제안: 기존 수집 글 행을 게시판별 인스턴스로 확장

아래 컬럼/프로시저 이름은 구현을 위한 제안이다. 별도 병렬 게시글 시스템이나 일반회원 가계정을 만들지 않는다.

### 4.1 목적 게시판과 중복 기준

1. `crawledCommunityTopic.boardKey`를 실제 `communityBoard.key` FK로 추가한다.
2. 기존 `(sourceSite, sourceExternalId)` 유니크를 `(sourceSite, sourceExternalId, boardKey)`로 변경한다.
3. 같은 게시판 재수집은 기존 행을 갱신하고, 다른 게시판이면 새 UUID 행을 만든다.
4. existing/known 조회와 모든 UPDATE 조건에 boardKey 또는 topic ID를 사용한다. sourceExternalId만으로 다른 게시판까지 갱신하지 않는다.
5. 새 게시판 행에는 원본 수집 데이터만 복제/수집한다. 다른 게시판 관리자 수정본이나 밤비 이용자 댓글은 복사하지 않는다.
6. 삭제/복구는 개별 topic ID 단위다. 한 게시판에서 삭제해도 다른 게시판의 행은 유지한다. 재수집도 삭제 표시를 되살리지 않는다.
7. 게시판 삭제 검사에 수집 글 존재 여부도 반영한다. FK 연쇄 삭제로 글·댓글을 잃지 않게 한다. 비활성·읽기전용을 포함한 모든 실제 게시판을 선택·수집 대상으로 제공한다. 베스트만 제외한다. 선택 가능 여부와 이용자 공개·열람 권한은 구분한다.

### 4.2 원본과 관리자 수정값

- 원본 title/body/sourcePostedAt/comments는 원본 수집값으로 유지한다.
- 관리자 편집값은 별도 `editedTitle`, `editedBody`(기존 Tiptap JSON 계약), `editedAt`, `editedByUserId`로 저장한다.
- `activityAt`은 글 또는 수집 댓글을 마지막으로 편집해 노출 기간이 다시 시작된 시각이다. 글 본문 편집 여부와 댓글 편집 이벤트를 구분한다.
- 글의 익명 작성자·등급 전환 여부는 글 자체의 editedAt으로 판정한다. activityAt만 존재하는 댓글 편집 건을 글 자체 편집으로 간주하지 않는다. 각 수집 댓글의 이름·등급은 해당 댓글 편집행 존재 여부로 독립 판정한다. 글을 편집해도 미편집 댓글의 작성자·등급은 바꾸지 않는다.
- 유효 제목/본문은 편집값이 있으면 편집값, 없으면 원본을 사용한다. 유효 목록 날짜는 activityAt이 있으면 해당 값, 없으면 sourcePostedAt을 사용한다.
- 관리자 작업 감사 기록은 기존 모더레이션 기록 패턴을 재사용하고 실제 작업자 ID를 내부에 남긴다. 표시용 익명 정보와 작업자를 혼동하지 않는다.
- 취소·조회만으로는 수정일/활동시각을 갱신하지 않는다. DB 저장 성공 시 같은 트랜잭션에서 갱신한다.
- 관리자 동시 수정 충돌은 revision/updatedAt 검증으로 이전 내용 덮어쓰기를 방지하고 최신 내용을 다시 불러오도록 안내한다.

### 4.3 수집 댓글 수정

- 원본 수집 댓글 배열은 유지하고 각 댓글의 안정 식별자를 추가한다. 신규 파서는 원본 comment_id의 숫자를 사용한다.
- 과거 배열에는 ID가 없으므로 migration에서 topic ID와 원래 배열 위치를 이용해 안정적인 legacy 식별자를 부여한다. 본문을 수정해도 ID가 변하지 않아야 한다.
- 편집 메타는 신규 `crawledCommunityCommentEdit` 테이블로 구체화한다. `(topicId, sourceCommentId)` 복합 PK, editedBody(text), editedAt, editedByUserId를 저장한다. topic FK로 게시판별 편집을 분리한다. sourceCommentId의 해당 topic 소속은 서버에서 검증한다.
- 원본 comments가 non-null이면 원본 배열·댓글 ID를 고정한다. 현재 pending 판정은 body가 없으면 comments도 다시 쓰므로, 재수집 UPDATE를 '누락된 원본 필드만 채우기'로 바꿔 이 경로에서도 기존 댓글 배열과 legacy ID를 보존한다. 자동 댓글 최신화는 기존 fetch-once 정책대로 이번 범위에 추가하지 않는다.
- 원본 댓글 JSON에는 원본 ID 네임스페이스 `source:`와 과거 식별자 `legacy:`를 구분한다. 이는 회원 표시값이 아닌 식별자 형식이며 원본 배열 순서 변경으로 편집 대상이 바뀌면 안 된다.
- 서버는 topic에 실제 존재하는 수집 댓글 ID인지 검증한다. `communityComment.id`를 넣어 밤비 이용자 댓글을 편집하는 요청은 거부한다.
- 수집 댓글 편집 성공 시 해당 topic의 activityAt도 갱신한다. 다른 topic에는 전파되지 않는다.
- 본문·댓글의 기존 길이 제한·연락처 처리·금칙어 정책을 재사용한다. 원본 파서의 댓글 상한을 새 UI에서 임의로 바꾸지 않는다.
- 수집 댓글의 기존 순서는 유지하고 표시 날짜만 수정일로 바꾼다. 글 노출 순서 갱신과 댓글 순서를 혼동하지 않는다.

### 4.4 등급 참조

- 일반 등급 이름을 매 요청마다 문자열 검색하거나 0포인트 등급이라고 추정하지 않는다.
- 사용자 승인: 기존 수집 설정에 편집 글 표시용 grade FK를 저장하고 기존 등급 목록에서 선택한다. 표시는 해당 행의 현재 값을 기존 badge 컴포넌트로 렌더한다.
- 글·댓글에 개별 grade FK 스냅샷은 저장하지 않는다. 이미 편집된 글·댓글도 전역 설정의 최신 grade FK를 조회한다. 설정의 선택 등급 변경은 과거 편집분까지 반영하되 글/댓글 수정 날짜·activityAt·30일 노출 기간을 갱신하지 않는다.
- 등급 설정 저장과 기존 등급 이름·색·아이콘 수정 성공 시 해당 등급을 소비하는 목록·상세·댓글·미리보기 캐시를 무효화한다. 수정 여부는 R11의 독립 판정을 유지한다.
- 참조된 등급 삭제는 기존 삭제 검사에 반영해 깨진 참조/임의 다른 등급 대체를 막는다. 미설정 상태에서 저장을 시도하면 명확한 설정 필요 오류를 반환한다.
- 가짜 회원/포인트 거래/본인인증 데이터를 생성하지 않는다. 수집 글 표시 속성만 부여한다.

## 5. API 계약과 수집 실행

| 기존/확장 지점 | 변경 내용 |
|---|---|
| getSettings/updateSettings | 목적 boardKey 저장·조회. 실제 DB 게시판 존재를 검증하되 비활성·읽기전용이라는 이유로 수집 선택을 거부하지 않는다. |
| runNow | community인 경우 화면의 boardKey를 전달. 공고 실행은 기존 계약 유지. |
| runCrawlTick/runCommunityPass | 회차 시작 때 boardKey를 확정해 목록·상세 전체에 전달. 공유 설정을 루프 안에서 다시 읽지 않는다. |
| crawlRun | 목적 게시판 식별자를 남겨 어느 게시판으로 실행됐는지 운영자가 확인 가능하게 한다. 원본 게시판명과 목적 게시판을 구분한다. |

| updateTopic(신규 adminProcedure 제안) | 제목·Tiptap 본문 검증, 편집값 저장, activityAt 갱신, 감사 기록. 일반 communityPost ID 거부. |
| updateSourceComment(신규 adminProcedure 제안) | 수집 댓글 소속 확인, 편집값 저장, activityAt 갱신, 감사 기록. 밤비 댓글 ID 거부. |

- 즉시수집 성공 응답은 시작 접수이며 수집 완료와 구분한다. 기존 회차 진행/오류 UI를 재사용한다.
- 같은 게시판의 재실행·동시 실행에 새 글이 중복되지 않도록 DB 유니크와 기존 회차 직렬화를 함께 유지한다.
- 진행 중 수집과 편집이 겹쳐도 원본 필드만 수집기가 갱신하므로 편집 메타는 보존한다.
- 설정 미선택/삭제된 게시판에서 다른 게시판으로 조용히 폴백하지 않는다. 기존 데이터와 최초 목적지는 현재 밤문화 이야기 연결을 보존한다. 사용자가 선택을 바꾼 뒤 저장하면 이후 예약 수집에 적용한다.

## 6. 목록·상세·권한 전파

1. `work_talk` 고정 UNION을 요청 boardKey의 순수 글 + 해당 boardKey의 수집 글로 일반화한다. 수집 목적지만 바꾸고 기존 목록 조건을 빠뜨리지 않는다.
2. 목록 items/totalCount/검색/overview/이전글·다음글은 같은 게시판 조건과 유효 날짜를 사용한다. 30일 상수는 기존 상수를 참조한다.
3. 관리자 수정 글은 자체 글과 함께 유효 날짜 기준 최신순으로 정렬한다. 기존 `is_crawled` 강제 후순위를 수정 글에 적용하지 않는다. 수정 전 수집 글의 기존 후순위와 공지·이벤트 고정 우선순위는 유지한다. 글과 수집 댓글 수정 모두 같은 정렬 함수를 사용한다.
4. 상세는 topic에서 실제 boardKey를 읽어 접근 가드를 적용한다. URL이나 클라이언트가 전달한 게시판을 신뢰하지 않는다.
5. 비밀게시판은 수정 전부터 여성·밤비로 표시하고 실제 reader/actor·잠금·제목/본문 마스킹 규칙을 재사용한다. 수집 상세·댓글도 해당 게시판 권한을 먼저 검사한다. 포인트 차감·열람 구매·구매 이력은 추가하지 않는다. 기존 에디터 이미지 업로드·렌더 구조를 그대로 재사용한다.
6. 법률자문·비활성·읽기전용도 수집 목적지 목록에 포함한다. 이는 공개 권한을 풀라는 요구가 아니다. 기존 게시판의 강제 잠금·역할·활성 정책을 재사용하고, 소유 회원이 없는 수집 글에 임의 소유자나 공개 예외를 만들지 않는다. 기존 계약으로 표현할 수 없는 경우만 구현 전에 사용자에게 구체적 정책을 확인한다.
7. 밤비 이용자 댓글 생성·답글·목록도 실제 topic.boardKey의 가드를 사용한다. 수집 댓글 편집 API를 추가한다고 기존 댓글 가드를 약화하지 않는다.
8. 수집 상세 ID는 전역 UUID이므로 기존 `/seeker/community/crawled/[id]`를 유지할 수 있다. 목록/이전/다음 이동은 응답의 실제 목적 board slug를 사용한다.
9. 기존 공개 `/board` 경로의 노출 범위는 변경하지 않는다. 수다방·메인에서 기존 overview를 소비하는 위치에는 기존 배치 안에서 해당 게시판 결과가 반영된다.
10. 베스트는 수집 목적지 선택에서 제외한다. 신규 게시판 추가가 자동으로 수다방 홈 배치까지 변경한다는 의미는 아니다.

## 7. 화면 구현

- 빨간 표시 위치: 기존 크롤러 카드의 마지막 실행 안내 아래/즉시수집 행 왼쪽에 라벨 있는 Select 배치. `communityBoards.list`(adminProcedure)를 재사용한다. `listActive`는 비활성 게시판을 누락하므로 사용하지 않는다. 실제 label/key와 sortOrder를 사용하고 best 가상 게시판을 덧붙이지 않는다.
- 현재 페이지를 연 채 다른 화면에서 게시판을 추가해도 반영되도록 기존 query invalidation + 드롭다운 열 때 재조회/창 focus 재조회를 활용한다. 하드코딩된 배열이나 새로운 폴링 주기를 만들지 않는다.
- 로딩/실패/게시판 없음 상태를 구분한다. 조회 실패를 빈 목록이나 밤문화 이야기로 대체하지 않는다.
- 크롤러 목록과 수집 상세의 편집 버튼은 같은 관리자 편집 경로로 이동한다. 목록에서 들어오면 돌아갈 페이지·탭을 보존한다.
- 기존 CommunityPostForm의 표시/검증/에디터를 재사용하되 admin-crawled 편집 모드를 명시한다. 일반회원/게스트 저장 mutation을 우회해서 호출하지 않는다.
- 일반 게시판 편집 작성자 표시는 익명 ㅇㅇ, 비밀게시판은 기존 밤비 표시를 사용한다. 관리자 세션 이름을 자동 채우지 않는다.
- 이미지 삽입·서식은 기존 업로드와 Tiptap 렌더 경로를 재사용한다. 확인 결과 `parseCommunityBody`는 plain text를 받으면 undefined를 반환한다. 따라서 편집 전용 어댑터로 원본 줄바꿈을 paragraph/hardBreak text 노드로 옮겨 doc JSON을 생성한다. 원문을 HTML로 해석하지 않고 빈 줄·따옴표·한글을 보존한다.
- 수집 상세의 현재 `<p>{topic.body}</p>` 분기는 편집된 리치 본문을 렌더하지 못한다. 편집 본문은 기존 `community-post-detail-parts.tsx`의 읽기 전용 Tiptap 뷰어를 재사용하고, 미편집 본문만 기존 평문 렌더를 유지한다.
- 댓글 편집은 해당 수집 댓글 옆 관리자 편집 버튼과 기존 댓글 편집 UI를 재사용한다. 다른 사람의 밤비 댓글에는 이번 기능의 편집 버튼을 추가하지 않는다.
- 저장 중 중복 제출 방지, 실패 시 입력 보존, 취소 시 무변경, 성공 시 목록·개수·상세·overview·이전/다음·관리자 목록 캐시를 해당 쿼리 키로 갱신한다.

## 8. migration과 기존 데이터

- 현재 develop 마지막 migration은 `0115_user-presence`. 다음 후보 번호는 0116이나 실제 생성 직전 최신 develop을 재확인하고 Drizzle이 생성한 이름을 문서에 기록한다.
- 작업 순서: nullable 컬럼 추가 → 기존 글을 현재 밤문화 이야기 게시판에 backfill → 누락/중복 검증 → FK·NOT NULL·복합 유니크 전환. 기존 topic UUID와 모든 댓글 연결을 유지한다.
- 기존 sourceSite/sourceExternalId, 삭제 표시, 수집 댓글, 연결된 밤비 댓글, 댓글 알림 대상 ID를 보존한다.
- 실제 적용 이력을 조회하기 전에는 파일 journal 정상 여부를 DB 적용 완료라고 기록하지 않는다.
- SQL/journal/snapshot prevId 체인, 번호 중복, develop 재통합 후 충돌을 검증한다. 기존 migration 수정·db:push·강제 덮어쓰기는 하지 않는다.
- 대표 데이터 검증: 원본 X의 기존 밤문화 topic ID 유지; 새 자유수다 topic ID 생성; 두 행에 밤비 댓글이 교차 연결되지 않음; 기존 removedAt 보존.

## 12. 추가 질문에 대한 사용자 확정 답변

### Q1. 기존 데이터와 최초 선택값

답변: 기존 데이터는 그대로 유지한다. 기존 topic ID·밤문화 이야기 연결·수집 댓글·밤비 댓글·삭제 상태를 보존한다. 최초 목적지도 기존 밤문화 이야기를 유지한다.

### Q2. 비밀게시판의 수정 전 표시와 실제 권한

### 14.2 추가 데이터 계약

- topic 추가 필드: boardKey(FK), editedTitle(nullable), editedBody(nullable doc JSON string), editedBodyText(nullable), editedAt(nullable), editedByUserId(nullable FK), activityAt(nullable), editRevision(integer, default 0). 등급은 전역 설정 FK만 사용하며 각 글·댓글에 등급 스냅샷을 추가하지 않는다.
- 설정 추가 필드: crawlCommunityBoardKey(FK), crawledCommunityEditorGradeId(nullable FK). 기존 setting row가 없어도 migration에서 기존 설정 생성 패턴을 이용해 기본 목적지를 보존한다. grade는 임의 자동 선택하지 않는다.
- crawlRun 목적 게시판 기록은 실행 당시 목적지를 표시한다. 공고 회차와 과거 회차는 nullable이다. 과거 회차에 근거 없는 목적지를 생성하지 않는다.
- editedBodyText는 기존 extractTiptapText로 저장 시 계산한다. 검색은 editedTitle ?? title, editedBodyText ?? body에 기존 likePattern을 사용한다. 원본 단어로만 검색되어 편집 글이 누락되는 오류를 막는다.
- 목록 썸네일은 기존 Tiptap 이미지 추출을 재사용해 편집 본문에만 적용한다. 목록 응답에 전체 원본·편집 본문을 싣지 않는다.
- 유효 댓글 수: 수집 comments가 null이면 기존 목록 commentCount 폴백, 수집 완료 후에는 실제 comments.length + 현재 공개 밤비 댓글 수. 관리자의 본문 편집은 댓글 개수를 늘리지 않는다.
- 기존 글 migration은 원래 topic ID를 유지하므로 밤비 댓글 FK·알림 딥링크를 바꾸지 않는다. 새 게시판 topic에는 새로운 ID를 사용하며 기존 밤비 댓글을 복사하지 않는다.
- 삭제된 게시판으로 진행 중인 수집이 조용히 다른 게시판에 저장되지 않도록 목적지 FK와 삭제 검사를 설정·topic·진행 중 회차와 함께 검토한다. 비활성화는 삭제와 다르며 선택·수집을 계속 허용한다.

### 14.3 저장 트랜잭션과 실패 처리

1. adminProcedure로 실제 관리자 권한 확인.
2. topic ID 존재·종류·expectedRevision 확인. 수집 댓글은 같은 topic의 원본 배열 ID 존재까지 확인.
3. 기존 제목 길이·assertTiptapDoc·extractTiptapText·금칙어 검사 재사용. 원본 수집 plain text 10,000자 상한과 편집기 JSON 30,000자 상한을 혼동하지 않는다. 해당 기존 상수가 파일 내부 상수라면 공용 정책 파일로 승격해 한 곳에서 참조한다.
4. topic revision 조건부 UPDATE로 경쟁을 검증하고 같은 트랜잭션에서 편집값/댓글 편집행/활동시각/감사 기록을 저장한다. 실패하면 전부 롤백한다.
5. 응답에는 저장된 revision과 실제 표시값을 반환한다. 클라이언트 Date.now로 날짜를 만들어 먼저 확정하지 않는다.
6. 이름·성별·등급은 서버가 정책과 설정에서 계산한다. 클라이언트가 관리자 실명, 다른 gradeId, 성별을 넣어도 허용하지 않는다.
7. 취소/실패는 활동시각과 30일 기간에 영향을 주지 않는다. 수집 작업도 활동시각을 늘리지 않는다.

- [ ] 댓글만 편집하면 해당 댓글 이름·등급만 변경되고 글 작성자·등급은 유지된다. 글 activityAt·정렬·30일 기간은 갱신된다. 글만 편집하면 미편집 댓글의 이름·등급은 유지된다.
- [ ] 수집 중 설정의 목적지를 바꿔도 기존 회차의 남은 상세가 새 게시판으로 이동하지 않는다.
- [ ] 수정되지 않은 과거 데이터의 본문·댓글·원본 날짜·기존 ID·삭제 상태가 migration 전후 동일하다.

### B1. 비밀게시판 최종 범위 — 확정

사용자 최종 지시: 실제 존재하는 비밀게시판 권한과 `밤비·여성` 표시 규칙을 적용한다. 남성 포인트 열람 기능은 이번에 추가하지 않는다. 비용·차감 주기·열람 구매 DB/API/UI를 생성하지 않는다.

### B2. 수집 댓글만 수정한 경우 글 작성자 표시 — 확정

사용자 답변: 별도로 적용한다. 수집 댓글만 수정하면 해당 댓글의 이름·등급·날짜만 변경하고 글 작성자·등급은 그대로 유지한다. 글의 최신순·30일 재시작은 기존 확정대로 적용한다. 비밀게시판 여성·밤비 표시는 수정 전후 모두 유지한다.

### B3. 선택 등급 자체를 나중에 바꾸는 경우 — 확정

사용자 답변: 과거에 편집한 글·댓글에도 변경된 등급을 적용한다. 전역 설정 FK를 사용하며 개별 편집 시점의 등급을 스냅샷으로 고정하지 않는다. 이름·아이콘·색도 참조된 등급의 현재 값을 따른다.
