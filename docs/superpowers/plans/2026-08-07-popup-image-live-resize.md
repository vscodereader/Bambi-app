# 모바일 팝업 이미지 실시간 크기 조절 수정 설계

> **상태:** 2026-08-07 사용자 확정 설계. 구현 전 설계서이며 이 문서 작성 시점에는 기능 코드를 변경하지 않는다.

**Goal:** 운영자 팝업 관리의 모바일 이미지 편집기에서 크기 수치만 변하고 화면의 이미지·선택선·핸들이 그대로인 오류를 수정한다. 운영자가 8방향 핸들을 드래그하거나 숫자를 입력하면 실제 미리보기 이미지가 즉시 같은 비율로 변하고, 저장된 크기가 공개 팝업 크기에 그대로 반영되게 한다.

**Architecture:** 저장 크기(`contentWidth`, `contentHeight`)와 화면에 그리는 선택 박스를 하나의 상태에서 파생한다. 편집 영역은 `ResizeObserver`로 실제 가용 너비를 측정하고 높이는 viewport의 `70vh`를 상한으로 사용한다. 이미지, 선택 테두리, 8개 핸들은 동일한 좌표계를 공유한다. 모바일의 전역 반응형 이미지 규칙이 편집 이미지만 별도로 축소하지 못하도록 편집기 내부 크기 계약을 명시적으로 적용한다.

**Tech Stack:** React 19, Next.js 16 App Router, TypeScript, shadcn/ui, Tailwind CSS v4, Vitest.

## 작업 및 브랜치 규칙

- 기준 브랜치는 설계 시작 시점의 최신 `origin/develop`이다.
- 작업 브랜치는 `fix/popup-image-live-resize`다.
- 별도 worktree `C:\Users\user\bambi\.worktrees\popup-image-live-resize`에서 작업한다.
- 설계서를 먼저 작성하고 사용자 확인 뒤 구현한다.
- 사용자의 별도 요청 전에는 commit·push·PR 생성을 하지 않는다.
- 기존 팝업 관리, 저장 전 draft, 취소, 실행 취소, 이미지 자르기 기능을 재사용하며 별도 편집기를 중복 구현하지 않는다.
- UI는 기존 shadcn/ui와 Tailwind 디자인 토큰을 사용한다. 인라인 스타일과 새 CSS 파일은 만들지 않는다.
- DB와 API 저장 구조는 변경하지 않는다. 이번 수정에는 migration이 없다.

## 확인된 원인

현재 `PopupImageEditor`는 다음과 같이 동작한다.

1. 드래그하면 `contentWidth`와 `contentHeight` 숫자는 정상적으로 갱신된다.
2. Next.js `Image`에는 갱신된 `width`, `height`가 전달된다.
3. 그러나 모바일에서 이미지에 적용되는 반응형 최대 너비 규칙 때문에 편집 영역보다 큰 여러 크기가 모두 같은 편집 영역 너비로 축소된다.
4. 선택 테두리와 핸들은 축소된 이미지 외곽에 붙으므로 `465 × 406`과 `565 × 475`처럼 서로 다른 수치도 화면에서는 같은 크기처럼 보인다.

따라서 데이터 저장 문제가 아니라, 모바일 편집기의 논리 크기와 실제 렌더링 크기가 분리된 WYSIWYG 오류다.

## 확정 동작

### 1. 크기 조절 규칙

- 이미지 선택 시 네 모서리와 상·하·좌·우를 합친 8개 핸들을 유지한다.
- 네 모서리 핸들은 드래그 시작 시점의 이미지 비율을 유지한다.
- 좌·우 핸들은 높이를 유지하고 너비만 변경한다.
- 상·하 핸들은 너비를 유지하고 높이만 변경한다.
- 어느 핸들이든 반대편 경계는 고정한다.
- 드래그 중 매 pointer move마다 이미지, 선택 테두리, 핸들 위치, 표시 크기 숫자를 함께 갱신한다.
- pointer를 놓은 뒤에도 해당 이미지는 선택된 상태를 유지한다.
- 이미지 바깥 편집 영역을 누르면 선택을 해제한다.

### 2. 최소·최대 크기

- 최소 크기는 기존과 동일하게 `50 × 50px`이다.
- 최대 너비는 현재 모바일 편집 영역 안쪽의 실제 가용 너비다.
- 최대 높이는 현재 viewport의 `70vh`다.
- 이미지가 최대 너비 또는 최대 높이를 넘지 않도록 제한한다.
- 모서리 드래그는 비율을 유지한 상태에서 먼저 도달하는 최대 경계에서 멈춘다.
- 변 핸들은 해당 축의 최대 경계에서만 멈추고 다른 축은 바꾸지 않는다.
- 편집 영역 크기가 orientation change, 브라우저 UI 변화 또는 반응형 레이아웃 변경으로 달라지면 최대 경계를 다시 계산한다.

### 3. 숫자 입력

- 현재 `표시 크기`의 너비·높이 숫자 입력을 유지한다.
- 입력 중 값을 지울 수 있어야 하며 빈 문자열을 즉시 `0`이나 최소값으로 되돌리지 않는다.
- 입력 확정 시 정수가 아니거나 최소값보다 작으면 `50`으로 보정한다.
- 최대값을 초과하면 해당 편집 영역의 최대값으로 보정한다.
- 최대값으로 보정될 때 `편집 영역 최대 크기까지만 설정할 수 있습니다.` 안내를 표시한다.
- 너비 입력은 너비만, 높이 입력은 높이만 바꾼다. 숫자 입력에는 모서리 비율 고정을 강제하지 않는다.
- 보정된 최종 숫자와 실제 이미지 외곽 크기는 항상 일치해야 한다.

### 4. 업로드 직후와 기존 저장 이미지

- 업로드한 이미지의 자연 크기가 편집 영역 최대값 이내이면 자연 크기를 초기 표시 크기로 사용한다.
- 자연 크기가 편집 영역보다 크면 비율을 유지해 최대 편집 영역 안으로 축소한 값을 초기 표시 크기로 사용한다.
- 기존 저장 이미지가 현재 모바일 편집 영역 최대값보다 크면 편집 진입 시 비율을 유지해 가용 영역 안에서 보이게 하고, 운영자가 실제 resize를 시작하거나 숫자 입력을 확정할 때 제한된 draft 크기를 적용한다.
- 단순히 편집 화면을 열었다는 이유만으로 서버 저장값을 변경하지 않는다.
- 저장 버튼을 누르기 전까지 모든 변경은 기존 팝업 카드의 draft에만 존재한다.

### 5. 저장·취소·실행 취소

- 저장 성공 전까지 공개 팝업에는 변경된 크기를 반영하지 않는다.
- 취소하면 이미지 크기를 포함한 해당 팝업의 모든 미저장 변경을 마지막 서버 저장본으로 되돌린다.
- resize 시작 시 한 번의 실행 취소 단위를 기록하고, 한 번의 연속 드래그를 여러 undo 단계로 쌓지 않는다.
- 숫자 입력 확정도 하나의 실행 취소 단위로 기록한다.
- 저장 성공 후 기존 규칙대로 실행 취소 이력을 초기화한다.
- 원본 이미지 Base64와 편집 이미지 분리 저장 계약은 변경하지 않는다.

## 구현 설계

### `popup-image-editor.tsx`

- 편집 캔버스 DOM ref와 `ResizeObserver`를 추가해 실제 내부 가용 너비를 상태로 관리한다.
- viewport 높이 변경을 반영해 `70vh` 최대 높이를 계산한다.
- `resize()` 순수 함수가 최소값뿐 아니라 현재 최대 너비·높이를 인자로 받아 clamp하도록 확장한다.
- 모서리 비율 유지 clamp, 좌우 단일 축 clamp, 상하 단일 축 clamp를 각각 분리해 테스트할 수 있게 한다.
- 편집 이미지에 암묵적인 `max-width: 100%` 축소를 맡기지 않고 계산된 실제 렌더 크기를 명시한다.
- 이미지 wrapper가 계산된 렌더 너비·높이를 차지하게 하고 이미지, outline, handle을 모두 wrapper 기준으로 배치한다.
- 터치 드래그 중 페이지 스크롤이나 브라우저 제스처가 resize를 가로채지 않도록 기존 `touch-none`과 pointer capture를 유지한다.
- `pointercancel`에서도 drag 상태를 정리하되 이미지 선택 상태는 유지한다.
- 숫자 입력에는 편집 중 문자열 상태를 두고 `blur` 또는 `Enter`에서 검증·보정한다.

### `popup-management.tsx`

- 기존 `contentWidth`, `contentHeight` draft와 `update()` history 계약을 유지한다.
- 업로드 직후 자연 크기와 편집 영역 최대 크기의 초기 fit 계산 경계를 편집기와 공유한다.
- resize 시작과 숫자 입력 확정이 정확히 한 번의 history snapshot을 만들도록 이벤트 경계를 정리한다.
- 기존 저장·취소·원본 초기화·복사·붙여넣기 동작은 변경하지 않는다.

### 공용 계산 함수

- DOM에 의존하지 않는 다음 계산을 순수 함수로 분리한다.
  - 최소·최대 범위 clamp
  - 원본 비율을 유지하는 편집 영역 fit
  - 8방향 핸들별 다음 크기 계산
  - 최대 경계 도달 시 모서리 비율 유지 계산
- 순수 함수는 web 단위 테스트에서 검증한다.

## 테스트 계획

### 단위 테스트

- `465 × 406`에서 `565 × 475`로 변경하면 계산된 렌더 박스도 더 커진다.
- 모서리 네 방향은 시작 비율을 유지한다.
- 좌·우 핸들은 너비만 바뀌고 상·하 핸들은 높이만 바뀐다.
- 각 핸들의 반대편 경계가 고정된다.
- 최소 `50 × 50px` 아래로 줄어들지 않는다.
- 최대 너비와 `70vh`를 넘지 않는다.
- 숫자 입력의 빈 문자열 편집이 가능하고 확정 시 올바르게 보정된다.
- 최대값 초과 입력은 최대값으로 보정된다.
- 연속 드래그가 실행 취소 한 단계로 기록된다.

### 모바일 수동 검수

1. `/moderator/popups`에서 이미지형 팝업을 열고 `팝업창 사이즈 조절`을 선택한다.
2. 이미지를 선택해 8개 핸들이 이미지 외곽에 정확히 표시되는지 확인한다.
3. 모서리를 안쪽으로 드래그해 이미지·테두리·핸들이 함께 실시간으로 작아지는지 확인한다.
4. 다시 바깥쪽으로 드래그해 편집 영역 최대 크기에서 멈추는지 확인한다.
5. 좌·우 핸들로 너비만, 상·하 핸들로 높이만 변경되는지 확인한다.
6. `465 × 406`과 `565 × 475`가 가능한 편집 영역에서는 두 크기가 실제로 다르게 보이는지 확인한다.
7. 숫자를 전부 지운 뒤 다시 입력할 수 있는지 확인한다.
8. 최대값을 넘는 숫자를 넣으면 보정과 안내가 표시되는지 확인한다.
9. resize 후에도 이미지 선택이 유지되고 빈 배경을 누르면 선택이 해제되는지 확인한다.
10. 취소하면 이전 저장 크기로 돌아가고 저장하면 메인페이지 팝업에 같은 크기 계약이 반영되는지 확인한다.
11. 세로·가로 화면 전환 후 편집 영역 최대값이 다시 계산되고 이미지가 영역 밖으로 넘치지 않는지 확인한다.

## 완료 기준

- 모바일에서 숫자만 바뀌고 이미지가 그대로인 현상이 재현되지 않는다.
- 표시 숫자와 이미지 선택 박스가 동일한 크기 상태를 사용한다.
- 드래그하는 동안 이미지와 8개 핸들이 끊김 없이 함께 움직인다.
- 최소·최대 제한, 비율 유지, 단일 축 resize가 확정 계약대로 동작한다.
- 저장 전 draft, 취소, 실행 취소, 원본 보존 등 기존 팝업 편집 기능에 회귀가 없다.
- 관련 테스트와 정적 검사가 통과한다.
